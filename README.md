# Mintlify 文档站搭建、迁移与维护 SOP

一套可反复使用的文档站生产流程，帮助产品、内容、技术写作与 AI 协作角色，将产品目标、现有帮助中心、文章清单或本地 HTML，转化为可维护、可预览、可发布、可持续更新的 Mintlify 文档站。

核心 SOP： [Mintlify文档站搭建迁移与维护SOP.md](Mintlify文档站搭建迁移与维护SOP.md)

## 能力概览

- **从零搭建**：从目标读者和关键任务出发，规划信息架构、路由、导航、页面模板、品牌资源和最小可运行站点。
- **旧站迁移**：将已授权的帮助中心、文章清单或 HTML 转为规范 MDX，并同时处理图片、GIF、视频、链接、锚点、旧路由和重定向。
- **持续维护**：将产品更新线索转为可核验事实，评估影响页面，同步更新文档、更新日志、导航与搜索入口。
- **体验与质量控制**：覆盖桌面/移动端、浅色/深色模式、目录、代码块、表格、断链、资源可用性和托管端表现。
- **受控发布**：明确本地验证、托管预览、Git 推送、PR、生产发布和 DNS 修改的确认边界与回滚方法。

## 为什么具有高复用性

它不是某个产品的一次性写作说明，而是一条可迁移到不同团队、产品线和内容来源的生产线：

```text
业务输入 → 事实核验 → 信息架构 → 内容与资源迁移
→ 导航与链接 → 本地验证 → 托管验收 → 受控发布 → 持续维护
```

可复用的关键在于：

1. 三条路径统一在同一套阶段定义下：从零搭建、旧站迁移和日常维护均有输入、动作、产物、验收和失败处理。
2. 内容来源可替换：适用于文章清单、页面链接、本地 HTML、结构化导出、产品包、接口描述和实测结果。
3. 质量门可复用：页面、站点、内容事实、安全和发布均有独立检查项。
4. 权限边界清楚：Agent 可以完成结构化、迁移、核验与本地验证；远程写操作和正式发布必须获得明确授权。
5. 提供可直接套用的启动表、架构表、迁移记录、证据表、发布确认单和任务 Prompt。

## 新使用者如何开始

建议按以下顺序学习和执行：

1. 阅读 SOP 的“先看这一页”和“能力边界与角色分工”，明确谁负责业务事实、权限与验收。
2. 复制“项目启动输入表”，补齐产品、读者、内容来源、品牌、仓库、部署和公开范围。
3. 选择一条路径：
   - 没有现成站点：从零搭建；
   - 有旧帮助中心或 HTML：旧站迁移；
   - 已有站点且需要跟随产品迭代：日常维护。
4. 先确认信息架构和首批页面，再进行批量内容生成或迁移。
5. 每个阶段对照验收标准；本地通过后，仍需在 Mintlify 托管预览中完成最终验收。
6. 使用“发布前确认单”完成 Git 推送、PR、生产发布或 DNS 变更前的审批。

## 使用原则

- **结构先行**：先规划导航与路由，再迁移或撰写内容。
- **证据优先**：动态产品能力需要可复核的实际证据，不把公告、截图或线索直接当作最终事实。
- **迁移完整**：正文、媒体、链接、锚点、目录和移动端体验需要一起处理。
- **安全默认**：密钥、Cookie、环境文件、日志、抓取原始包与敏感截图不进入仓库。
- **发布受控**：本地预览不等于上线验收；外部写操作和正式发布均保留明确确认门。

## 适用对象

- 产品经理与产品运营：梳理用户任务、信息架构、首发范围和更新节奏。
- 技术写作者与开发者关系团队：建设开发者文档、操作指南、FAQ 与更新日志。
- 工程与运维团队：处理仓库、构建、部署、托管验收与回滚。
- 使用 AI 协作的团队：以 SOP 中的角色分工、模板和 Prompt 建立稳定的人机协作流程。

## 维护建议

当 Mintlify 的 CLI、配置格式、部署流程、导航机制或团队发布制度变化时，优先核对官方资料和真实工具输出，再更新 SOP 中的默认路径。历史兼容做法应保留在兼容性说明中，不应替代当前标准流程。
